结论速览

  1. 本质是"远程操作真人界面"，不是"破解接口"。脚本通过 W3C WebDriver 协议下发找元素 / 点击 / 刷新指令，走的是浏览器和安卓系统的官方自动化通道，没有调用大麦的下单接口，也没有处理验证码。
  2. 抢票的胜负手是"轮询节拍 + 命令往返次数"。PC 端靠 每 0.3 秒刷新一次页面、读一次按钮文案来撞开售瞬间；移动端靠关掉 UiAutomator2 的隐式空闲等待、改用坐标手势点击，把单步延迟压到百毫秒级。
  3. 稳定性靠"降级链"堆出来，而不是靠契约。勾观演人 4 套方法、提交订单 5 套方法、App 每个节点 3 个选择器——命中即返回，全部依赖对前端 class 名和中文文案的猜测，页面一改版就集体失效。

01项目定位

一个跑在本机上的单账号、单设备、串行执行的 UI 自动化脚本，目标是把「开售后一秒钟内的十几次点击」交给程序完成。

它是什么它不是什么
UI 层自动化：模拟人在页面上点已有按钮、卡片 不是协议逆向：没有构造下单请求、没有签名算法
依赖人工扫码登录，之后复用 Cookie 没有验证码识别、没有滑块破解
参数预置式定点狙击：城市/场次/票价/人数写死在配置里 不是"任意演出自动决策"的智能体
本机单进程工具，1000 余行核心逻辑 不是分布式、多账号、代理池集群
血缘关系 当前仓库是知名开源项目 WECENG/ticket-purchase 的 fork：保留上游提交历史与作者署名，在此基础上补了 Appium 安卓端实现（多数票只能在 APP 买）、性能参数调优、Poetry 依赖管理、pytest 骨架与中文文档。仓库本身 0 star、20 余次提交，属于个人自用/练手性质。

03底层通道：一次点击到底发生了什么

理解后面所有"提速技巧"的前提：每个动作都是一次 HTTP 往返，所以性能优化的方向只有两个——减少次数、减少每次内部的等待。

# Python 里写的一行代码
driver.find_element(By.CLASS_NAME, "buy__button__text").click()

# 实际发生的事（W3C WebDriver 规范，HTTP + JSON）
POST /session/{sessionId}/element        ← 查元素，一次往返
POST /session/{sessionId}/element/{eid}/click  ← 点击，再一次往返

# chromedriver 再把命令翻译成 Chrome DevTools Protocol
DOM.querySelector → Input.dispatchMouseEvent → 页面 JS 收到 onclick

移动端同理，链路更长一层：

Python(appium) → Appium Server → ADB 端口转发 → 设备内 UiAutomator2 服务
              → Accessibility / Instrumentation 指令 → 真实触摸事件
单次命令开销
十毫秒 ~ 百毫秒级
PC 一轮轮询
≈ 4~6 次命令往返
App 一次点击
≈ 1 次查找 + 1 次手势
性能上限来源
HTTP RTT + 驱动内部等待

正则从 Google Chrome 131.0.x 中截出 131。

STEP 3

04PC 端执行原理

一条 status 状态机，串起十几次点击；每一环都用"多策略降级 + 命中即返回"来换取在不确定页面上的存活率。

4.1 登录：Cookie 复用，而不是登录接口

首次运行走"人工扫码 + 落盘 Cookie"：循环比对 driver.title 字符串来判断扫码是否完成，成功后 pickle.dump(driver.get_cookies()) 存到 damai_cookies.pkl。

后续运行直接读回，逐条 add_cookie。这里有个必须踩过的顺序问题：

self.driver.get(self.config.target_url)   # ① 必须先落到 .damai.cn 域下
self.get_cookie()                        # ② 才能 add_cookie
# get_cookie() 内部：
cookie_dict = {'domain': '.damai.cn', 'name': name, 'value': value}

damai/concert.py:43-92

设计缺陷（可解释"偶发登录失效"） 保存时只取了 name / value，丢掉了 path、expires、httpOnly、sameSite；domain 还被硬写成 .damai.cn。所以它不是"标准 Cookie 持久化"，而是一次有损转存。

4.3 开售轮询：撞时间窗

这是整个 PC 端的心脏。它不预先"定点唤醒"，而是提前启动、然后无限刷新，每一次刷新读一遍按钮文案：

while not self._is_order_confirmation_page():
    buy_button = self._get_element_text_safe('buy__button__text', By.CLASS_NAME)

    if buy_button == "提交缺货登记":      # 还没开售
        self.driver.get(self.config.target_url)
        continue

    for text in ["立即预订", "立即购买", "缺货登记", "选座购买"]:
        if buy_button == text:
            self._click_element_safe('buy__button__text', By.CLASS_NAME)
            clicked_booking = True; break

    time.sleep(0.3 if fast_mode else 1)
    self.driver.refresh()

damai/concert.py:157-247

原理拆开看是三件事：

  • 票态信号 = 按钮文案。没开售时是"提交缺货登记"，开售后变"立即预订"——用文案差异代替读取任何接口返回值。
  • 时间窗 = max_retries（配置里 10000）× 每轮耗时。它撑住的是"从现在到开售"的整段时间，而不是精确到毫秒的那一刻。
  • 节拍 = fast_mode ? 0.3s : 1s。这个数字是命中率与服务器压力的直接权衡。
原理上的短板 没有服务端校时（NTP）、没有预热 DNS/TLS、没有提前建立连接，也没有"到点瞬间并发点击"。所以命中率取决于本地时钟误差 + 网络 RTT + 刷新节拍三者之和，属于"用频率换精度"。

4.4 选项匹配：子串包含 + 黑名单

城市、场次、票档共用同一个匹配器：不做精确匹配，做"配置值是页面文案的子串"，同时跳过含"无票/缺货/售罄"的卡片。

           and not any(kw in element.text for kw in ['无票', '缺货', '售罄']):

4.5 数量：点加号，或者直接改 v-model

主路径是找 cafe-c-input-number 的 + 按钮，点 N-1 次，然后回读输入框值做校验。主路径失败时，走一条"绕过组件"的路：

driver.execute_script("""
    arguments[0].value = '2';
    arguments[0].dispatchEvent(new Event('input',  {bubbles:true}));
    arguments[0].dispatchEvent(new Event('change', {bubbles:true}));
    arguments[0]._v_model = '2';
""", input_elem)

damai/concert.py:1354-1488

这是全文最值得记住的一个原理点：大麦前端是 Vue 体系，DOM 的 value 和组件状态是两套东西。 直接改 value 只骗了浏览器，没骗到 v-model；必须手动派发 input/change 事件，让框架的回调跑一遍，状态才会同步。这就是为什么 send_keys() 有时无效、而"改值 + 派事件"能生效。

05移动端执行原理

与 PC 端完全不同的加速哲学：PC 端靠"少睡多刷"，App 端靠拆掉 UiAutomator2 的隐式同步机制。因为多数票只能在 APP 买，这一条链路才是主战场。

5.1 会话：把会话直接开在已登录的 APP 上

capabilities 指定 appPackage=cn.damai、noReset=true，即复用设备上已有的登录态，跳过"启动 → 搜索 → 进详情页"的全部慢动作（前置条件：人工先把 APP 停在演出详情页）。同时把动画关掉、截图帧率降到 1、超时放宽，都是为了减少无关开销。

damai_appium/damai_app_v2.py:28-52

5.2 关键一步：关掉"等页面空闲"

UiAutomator2 默认在每次操作后等 Accessibility 事件流"稳定"再返回——这在普通自动化里是好事，在抢票里是致命延迟。所以脚本进场第一件事就是改设置：

设置项默认行为改成收益
waitForIdleTimeout等界面空闲再返回0不再等，直接返回
actionAcknowledgmentTimeout等动作确认0去掉确认等待
keyInjectionDelay逐字符输入间隔0输入零延迟
waitForSelectorTimeout500ms300ms查找更快失败/更快返回
ignoreUnimportantViews可开false保留完整视图树，避免元素丢失

damai_appium/damai_app_v2.py:54-66

配套的等待策略也变了：用 WebDriverWait(driver, 2) + presence_of_element_located，只等"存在"，不等"可点击"——把 Selenium 的智能等待压到最短，用"后面点击失败再兜底"来换速度。

5.3 点击通道：坐标手势比元素点击快

rect = el.rect                                  # 取元素矩形
x = rect['x'] + rect['width']  // 2
y = rect['y'] + rect['height'] // 2
driver.execute_script("mobile: clickGesture", {
    "x": x, "y": y,
    "duration": 50                            # 极短按压
})

damai_appium/damai_app_v2.py:68-96

原理：element.click() 要先算可点击点、走 UiAutomator 的"可点击性"探测、再等 settle；而 clickGesture 是直接给屏幕下发一次 30~50ms 的原生手势，一跳到位。这是 Appium 场景下最有效的单点提速手段。

批量勾观演人：把串行往返变成连点

普通写法是"找 A → 点 A → 找 B → 点 B"，N 个人就是 2N 次往返。改成先批量收集坐标，再连续点击，间隔 10ms：

  1. 遍历配置里的姓名，逐个 WebDriverWait(...presence...) 拿到元素并算出中心坐标，存进 coordinates；
  2. 再对坐标列表逐一下发 clickGesture(duration:30)，相邻点击只隔 0.01 秒。

damai_appium/damai_app_v2.py:97-125

5.4 一次原理性的妥协：票价按 index 选

APP 改版后，票价卡片的 text 变成空串，按文案定位彻底失效。作者的解法是退化成位置定位：

    By.ID, 'cn.damai:id/project_detail_perform_price_flowlayout')

target = box.find_element(
    AppiumBy.ANDROID_UIAUTOMATOR,
    f'new UiSelector().className("android.widget.FrameLayout")'
    f'.index({price_index}).clickable(true)')

                      {'elementId': target.id})

这是纯 UI 自动化绕不过去的宿命：一旦前端把语义信息抽走，自动化就只能退化到位置信息，而"第 5 个可点击的 FrameLayout"换一场演出就失效，因此配置里多了个要手调的 price_index。

5.5 会话生命周期：失败就重开

run_ticket_grabbing() 在 finally 里 driver.quit()；run_with_retry 最多 3 次，每次失败后重建会话。原理：Appium 会话一旦被异常页面状态卡住（弹窗遮挡、视图树脏），最快的恢复不是"在旧会话里挣扎"，而是丢掉会话重开。

06端到端时序

把所有环节串成一条时间线，能清楚看到它"抢"的到底是什么：不是抢网速，是抢"开售后第一次有效点击"的时间点。

T − 60s
环境自检与建会话

找 Chrome → 比对 chromedriver 主版本 → 启动浏览器；App 侧拉起 Appium 会话并改 update_settings。

T − 30s
恢复登录态，打开目标详情页

PC：get(target_url) → add_cookie；App：noReset 直接复用登录态。

T − 20s
详情页预选：城市 / 场次 / 票档 / 数量

这些控件开售前就可点，提前选好，开售瞬间只剩"点预订"一步。匹配方式：子串包含 + 缺货售罄黑名单。

T − 0s
开售判定：文案翻转

PC 每 0.3s refresh() 读一次按钮文案，从"提交缺货登记"变成"立即预订"即点；App 等"预约/购买"按钮出现即点（不用刷整页）。

T + 0.3s
进入结算页 → 勾观演人

四级降级依次尝试；App 端先批量取坐标再 10ms 连点。

T + 1s
提交订单

PC 五级降级；if_commit_order=true 才真正下单，否则停在支付前交人工确认——"半自动"是刻意的风险控制。

之后
挂起，等人付款

PC 端 time.sleep(300) 保持页面；订单有支付超时，脚本不接管支付环节。

它没有抢的那部分时间 没有校时、没有预热连接、没有并发、没有重试风暴。换句话说：它把"人手速"换成了"程序节拍"，但没有解决"网络与服务器侧"的排队问题——真实能否买到，仍取决于大麦的排队机制和库存释放。

08病根与局限

① 把前端实现细节当成了 API

定位依赖 buy__button__text、sku-tickets-card、item-content 这类 BEM 风格 class 名，以及"订单确认页""立即预订"这类中文文案。任何一个改名、改文案、改结构，整条链路就断在某个降级层。作者自己在 app.md 里已经撞过一次墙（票价 text 变空串），最后的解法是退到 index。

② 用 sleep 代替显式等待

PC 端几乎全部靠固定 sleep 猜页面加载时间：睡短了元素没出来，点了空；睡长了错过窗口。正确姿势是 WebDriverWait(...).until(EC.element_to_be_clickable)，但那和抢票的"快"天然冲突——这是同类脚本共同的取舍。

③ 没有风控对抗，成功率不可控

只有两条入门级反检测。面对设备指纹、行为轨迹、频控、库存排队，脚本没有任何对策；高频刷新本身还可能触发风控。它不是"稳抢工具"，而是"把点击自动化"的工具。

④ 工程瑕疵（不影响理解原理）

  • 模块用 from concert import Concert 导入，依赖当前工作目录，必须 cd damai 才能跑；
  • config.json 按相对路径读取，路径一变即失效；
  • 启动脚本里写死了 /Users/xxx/Library/Android/sdk 和某个 Poetry 虚拟环境的 python 绝对路径；
  • pyproject.toml 要求 --cov-fail-under=80，但现有测试只覆盖环境检查与目录结构，核心抢票逻辑基本没有有效单测；
  • 仓库里提交了真实观演人姓名（配置示例），属于个人信息，复用前应先替换并清理历史。
合规提示（技术分析不等于可用许可） 大麦《用户协议》禁止使用外挂或自动化程序抢票，命中后订单可能被取消、账号可能受限；若用于"代抢收费/囤票转卖"，还可能触及不正当竞争与网络安全相关法规。本文只做代码原理拆解，实际使用需自行评估风险。
